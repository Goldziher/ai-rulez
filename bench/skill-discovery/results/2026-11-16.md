# Skill discovery pilot, 2026-11-16

We ran 80 turns across Claude Code and Codex. Each case used one matched pair. We measured an 8-skill flat control,
8- and 128-skill nested catalogs, and a separate small nested pair with the generated `dynamic-skills` stub.
Each arm of the sibling walk resumed the same session for the second worksheet. Tool events referenced both worksheet
paths across all 16 resumed sequences.

## Positive tasks

“Selected” counts a tool action naming the expected skill. “Loaded” counts a tool result containing the code from
that skill's body. “Code in answer” includes exact answers and answers that also included explanation or Markdown.
Input totals include cached tokens. Body latency is measured only for observed loads, with misses shown in the
loaded column.

- The Claude native arm returned the code on every positive turn, usually within a sentence. Its connected bare MCP
  arm called discovery on two positive turns, and both calls led to a correct body read and code. The generated
  stub was listed in both MCP sibling turns, which made no discovery calls.
- Codex found and used MCP skills in every positive turn. In the 128-skill nested native sibling walk, it returned
  `NO-CODE` on both turns despite tool output containing the expected skill body's code. Read success and answer
  success are tracked independently.
- In the nested wrong-scope control, both native arms read a fixture skill body. Codex returned exactly `NO-CODE`.
  Claude returned the return code in response to the dispatch question. Both MCP arms returned exactly `NO-CODE`
  without a body read.
  All eight unrelated arithmetic controls answered exactly `42` without an observed fixture body read.
- No measured turns timed out or failed at the harness level. The scorer found zero direct read attempts against the
  external MCP catalog.

Claude reports first-request input usage in its first streamed message. Codex reports turn totals, so the Codex
rows use the equivalent total for the dedicated no-tool startup prompt. Treat these as within-harness comparisons.

Claude listed 8, 3, and 63 fixture skills at initialization for the flat small, nested small, and nested large native
arms. Its nested root listed a subset of the fixture while skill bodies in both sibling scopes were successfully
found during the native walk. Codex did not expose the equivalent initialized inventory. On the small nested
generated-stub startup pair, Claude observed 7,109 native input tokens and 7,673 with MCP and the stub. Codex
reported 18,745 for each arm. The empty MCP control still advertises the same two tools, and the measurements
include provider-side prompt construction and cache effects.

Observed process-launch-to-first-assistant-event times for the small flat native, MCP, empty native, and empty
MCP cases were 2.78 s, 1.74 s, 1.78 s, and 1.97 s in Claude Code and 7.96 s, 5.44 s, 4.35 s, and 4.56 s in Codex,
respectively. These include startup and model response time. Neither CLI reported the model-request dispatch time.

## Reproduce

- macOS 27.2.1 arm64, ai-rulez v5.13.3 and fixture version 1 at commit
  `9a5c06b079e51ea99b699cc898e11e82f8120b16`.
- SHA-256 of the extracted ai-rulez binary
  `b411218f0aabbe3a19475d6dbbe96c417279b97dce83f91903b61b26470d19a6`.
- Claude Code 2.1.325, `claude-sonnet-4-6`, low effort, signed-in Claude account. The CLI used project settings only
  and restricted built-in tools to Read, Skill, and ToolSearch. Hooks and auto-memory were disabled. Built-in
  plugins remained enabled in both arms. Session persistence was used only for the sibling walk.
- Codex CLI 0.169.0-alpha.11.1, `gpt-6.1-sol`, low effort, signed-in ChatGPT account with isolated Codex config
  and read-only sandbox. Both providers reported the requested model names or accepted the pinned model ID.
  Provider model revision identifiers were unavailable.
- Provider cache defaults stayed in force. We used fresh local workspaces and sessions for each arm, ran native
  first, and did not reset provider caches. Harnesses and the separately labeled size/stub series ran in parallel
  on the same host. Codex reported shell snapshot timeouts in some sessions, and its latency measurements include
  that initialization overhead.

Download and verify the release binary, then run the following from the repository root. Set `binary` to the
absolute path of the extracted executable. The two CLI accounts must already be signed in.

```sh
umask 077
work=$(mktemp -d)
for harness in claude codex; do
  python3 bench/skill-discovery/run.py "$harness" "$binary" "$work/$harness-pilot" --size small \
    > "$work/$harness-pilot.jsonl"
  python3 bench/skill-discovery/run.py "$harness" "$binary" "$work/$harness-large" \
    --size large --layout nested --task dispatch --task sibling-walk --task startup \
    > "$work/$harness-large.jsonl"
  python3 bench/skill-discovery/run.py "$harness" "$binary" "$work/$harness-stub" \
    --size small --layout nested --task sibling-walk --task startup --mcp-stub \
    > "$work/$harness-stub.jsonl"
done
python3 bench/skill-discovery/publish_results.py "$work/"*.jsonl > "$work/published.jsonl"
```

The runner uses the fixture prompts verbatim and records private tool events with monotonic arrival timestamps.
First-assistant time measures the first streamed Claude message or first completed Codex assistant text event.
Request dispatch timestamps were unavailable. First skill use measures the first tool result carrying the relevant
body marker. Sanitized measurements omit session IDs, raw text, local paths, credential material, and transcript
contents. The input totals break out cache reads and writes separately.

[Per-turn data](2026-11-16.jsonl) includes every measured turn. This pilot has one pair per configuration and
uses a single host with fixed arm ordering. Rates and medians describe these sessions. The full protocol still calls
for 20 pairs with alternating arm order per case, larger flat controls, and repeated startup attribution.
